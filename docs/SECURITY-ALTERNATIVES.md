# Другие способы проверки и снижения лишнего доступа Windows

22 октября 2026 года. Варианты выбраны по официальным материалам Microsoft, GitHub, VirusTotal, Inno Setup, Mandiant и SignPath. Изменения в этом документе не являются обещанием нулевого числа антивирусных срабатываний.

## 1. Убрать лишнее право чтения памяти процессов — реализовано

Из API VirusTotal получены отдельные отчёты CAPA, CAPE Sandbox, Jujubox и Zenbox по тестовому EXE `009c7a7be1b211aecc961f091069fa1c56dc1fc694829d5e57e376b02dd28b40`. Отдельно скачаны полные HTML-отчёты CAPE и Jujubox, сохранены как неисполняемые текстовые файлы и не открывались в браузере. API-ключ передавался только API VirusTotal, не передавался хранилищу при перенаправлении и не записан в отчёты.

В полном отчёте CAPE видна последовательность: NtOpenProcess для `explorer.exe` (PID 4240) с `PROCESS_VM_READ|PROCESS_QUERY_INFORMATION`, затем ReadProcessMemory для того же handle `0x30c`, чтение 8 байт. Есть адреса вызывающего кода, но сводка не связывает их с конкретным методом C#.

В наших исходниках `SingleInstance.FindExisting` перебирал процессы с окнами и читал `process.MainModule.FileName`, чтобы узнать, где лежит другой EXE. Для этой задачи перечислять модули и читать память процесса не требуется. Это правдоподобное объяснение части наблюдений, а не доказанная причина всех меток CAPE или Wacatac.

Теперь пути получаются через `QueryFullProcessImageNameW` с `PROCESS_QUERY_LIMITED_INFORMATION` (`0x1000`). Право `PROCESS_VM_READ` не запрашивается. Замена выполнена в поиске других копий, проверках путей браузеров и аутентификации родительского процесса обновления. Проверки PID, времени старта, пути, версии и хеша в обновлении сохранены. При отказе Windows код не пытается получить более широкие права.

Microsoft описывает ограниченное право, достаточное для [QueryFullProcessImageNameW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew), и отдельно показывает получение `PROCESS_VM_READ` в примере [перечисления модулей процесса](https://learn.microsoft.com/en-us/windows/win32/psapi/enumerating-all-modules-for-a-process).

Проверки: путь собственного EXE, путь контролируемого дочернего процесса, некорректный PID, отсутствующий процесс и три существовавшие проверки поиска DLL — 7 успешных проверок. Дочерний процесс является тестовой копией и завершается собственным сигналом; пользовательские приложения не закрывались.

## 2. Полностью воспроизводимая сборка — реализовано как отдельный режим

`tools/Build-VerifiedWindows.ps1` использует подписанный Microsoft компилятор Roslyn с `/deterministic+`, `/pathmap`, явным списком .NET Framework references и `/noconfig`. Результат сопровождается `build-manifest.json`: версия и хеш компилятора, хеши входных файлов, библиотек и EXE. Проверяется, что входные файлы не изменились во время компиляции. Нужны Visual Studio Build Tools; обычный `build.bat` остаётся доступен.

`tests/ReproducibleBuild.Tests.ps1` собирает одинаковые исходники из двух разных папок. Получились полностью одинаковые SHA-256, без маскирования времени или GUID. Изменение описания в AssemblyInfo тестовой копии изменило хеш, как и должно быть. После правки поиска путей процессных EXE проверка повторена и снова прошла.

Источники: Microsoft о [Deterministic](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/code-generation#deterministic) и [PathMap](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/advanced#pathmap). Польза здесь — возможность связать файл с точными входными данными. Переход на другой компилятор не доказывает безопасность и не является гарантированным способом уменьшения детектов.

## 3. Проверять уже готовый EXE — реализовано

`tools/Test-WindowsArtifact.ps1` и `tools/ArtifactInspection.cs` проверяют метаданные без запуска программы:

- ссылки на ожидаемые .NET Framework сборки с ожидаемыми версиями и public key token;
- список допустимых встроенных ресурсов и отсутствие PE-подобного payload под именем изображения;
- разрешённые системные DLL и атрибут поиска только в System32 для явных P/Invoke;
- прямые импорты операций работы с чужой памятью/потоками, которые текущей программе не нужны и требуют отдельного рассмотрения;
- фактически встроенный манифест `asInvoker`, `uiAccess=false`.

11 положительных и отрицательных тестов прошли. В том числе отклонены неподписанная DLL с именем системной сборки, неожиданная DLL, неограниченный поиск DLL, вложенный EXE, повышение прав при старте и ReadProcessMemory, переименованный через `EntryPoint`. Статический конструктор проверяемой фикстуры не выполняется. Оба реальных проверявшихся EXE — старой и новой схемы сборки — прошли политику состава.

Эта политика ограничивает состав, а не заменяет антивирус. Она не доказывает отсутствие опасных действий через разрешённые managed API или внутри CLR. Изменение допустимого состава должно сопровождаться обычным рассмотрением кода.

## 4. Независимый Windows runner — подготовлено, ещё не запускалось

Добавлен `.github/workflows/verify-windows-artifact.yml`: ручной запуск на `windows-latest`, минимальные права `contents: read`, отсутствие сохранённых Git credentials, actions закреплены полными commit SHA. Workflow выполняет проверки состава, ограниченного доступа к процессам, воспроизводимости, логики и UI, затем сохраняет EXE и свидетельства как тестовый артефакт. Ключ VirusTotal и публикация релиза не требуются.

Workflow пока только локальный: он не отправлен на GitHub и не запускался. Локальные сборки по-прежнему происходили на этом компьютере; их нельзя выдавать за результат чистой внешней Windows.

Для будущих публичных релизов можно добавить [GitHub artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations), связывающие файл с commit и workflow. Это не Authenticode и не гарантия безопасности. GitHub рекомендует аттестовать распространяемые артефакты, а не частые промежуточные тесты; поэтому в ручном тестовом workflow аттестация не включена.

## 5. Трассировка с происхождением вызовов — данные получены, причина установлена частично

[API VirusTotal](https://docs.virustotal.com/reference/get-all-behavior-reports-for-a-file) предоставляет данные отдельно по песочницам. Это полезнее общей сводки: CAPA описывает статические возможности кода, а CAPE и другие среды — собственные наблюдения. [Mandiant capa](https://mandiant.github.io/capa/) предназначен для поиска возможностей; запись о записи и запуске файлов сама по себе не устанавливает, что выполнялась вредоносная загрузка.

В нашем отчёте CAPA содержит 60 записей о возможностях, CAPE — 22 сигнатуры. Объединять эти числа в один независимый антивирусный вердикт нельзя. У каждой среды различается покрытие сценария. Обновление, UAC, подключение DNS и отмену нужно проверять отдельно.

Для дальнейшего локального/VM разбора подходит [Microsoft Process Monitor](https://learn.microsoft.com/en-us/sysinternals/downloads/procmon): журнал файлов, реестра, процессов, загрузок образов и стеки соответствующих операций. Он помогает установить происхождение загрузки DLL и записи файла, но не является универсальной трассировкой всех Win32 API чтения памяти. Новая захватывающая системные события сессия Procmon на пользовательском ПК в этой работе не запускалась.

## 6. Подпись без покупки сертификата — существует, но принятие не гарантировано

[SignPath Foundation](https://signpath.org/) предлагает бесплатное подписание для open-source. Это отдельный вариант от покупки личного сертификата.

[Условия](https://signpath.org/terms.html) включают открытую лицензию, сопровождаемый выпущенный проект, проверяемую автоматическую сборку, MFA и ручное одобрение подписания. Для форков и репутации готовых приложений есть дополнительные ограничения. Поэтому мы не утверждаем, что этот проект примут. Подпись выдаётся от имени фонда, не является гарантией отсутствия детектов; заявку, исходники и файлы фонду не отправляли.

Вместо ожидания общедоступного «белого списка» Microsoft предлагает [разработчику оспаривать конкретное определение](https://learn.microsoft.com/en-us/defender-xdr/developer-faq). Решение по заявке не обещано. Письма и обращения производителям в этой работе не отправлялись.

## 7. MSI вместо Inno — возможная отдельная инженерная работа

[Windows Installer](https://learn.microsoft.com/en-us/windows/win32/msi/windows-installer-portal) — встроенная служба установки с MSI-пакетами, управлением компонентами и откатом. Можно реализовать пакет без пользовательских CustomAction: приложение, лицензии, ярлыки, штатная установка и удаление. Это меняет механизм сопровождения, а не является доказанным лечением Wacatac.

Нужны проверки установки/переустановки, обновления, отказа от downgrade, удаления и взаимодействия с текущим самообновлением. Изменённый самообновлением EXE не должен конфликтовать со штатным ремонтом MSI. Inno сейчас не заменён; новый MSI не собирался.

[MSIX](https://learn.microsoft.com/windows/msix/package/signing-package-overview) требует подписи с доверием на целевой машине; самоподписанный сертификат не решает удобную массовую установку. Поэтому при текущем ограничении бюджета MSIX не выбран в качестве быстрого исправления.

## Результаты выполнения

- 11 проверок политики EXE — прошли.
- 7 проверок ProcessSecurity — прошли, включая контролируемый дочерний процесс.
- Полный набор логики Windows — прошёл с Roslyn; одна существующая live-проверка старых NRPT правил пропущена из-за отсутствия таких правил.
- Два реальных временных сценария обновления (портативное имя и SmartDNS.exe) — замена и перезапуск прошли. Фикстура использует стабильную версию 99.0.0 независимо от test-версии приложения; настоящее приложение не заменяется.
- Побайтовая воспроизводимость и отрицательная проверка изменения входа — прошли.
- 7 проверок UI motion готовой проверенной сборки — прошли.

Скрипты запускаются из корня проекта:

```powershell
./tests/ArtifactInspection.Tests.ps1
./tests/ReproducibleBuild.Tests.ps1
./tools/Build-VerifiedWindows.ps1 -OutputDirectory ./dist/verified
./tools/Test-WindowsArtifact.ps1 -File ./dist/verified/KodVsego_SmartDNS.2.23.2-test.1.exe
```

Ключа API в новых исходниках, workflow, документах и свидетельствах нет. Старые тестовые файлы в dist/2.23.2-test.1 не заменялись, новые варианты не загружались в VirusTotal. Поэтому прежние 4/71 и 5/69 нельзя представлять как результаты исправленной программы.
