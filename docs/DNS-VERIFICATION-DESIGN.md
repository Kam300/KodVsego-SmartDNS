# Проверка применения DNS и внешнего маршрута

Исследование от 25 октября 2026 года. Это проект изменений, не описание уже реализованной функции. Код сторонних проектов не запускался и не переносился; настройки ПК и роутера не менялись.

## Уточнение: сначала официальный чекер провайдера

По предложению пользователя проверены исходники официальных сайтов и выполнены запросы трёх чекеров через текущий системный путь Windows, без принудительной подстановки проверяемого DNS, прокси и изменения настроек. Для провайдера с подходящим чекером этот механизм должен быть основным; универсальное сравнение рекурсивных узлов — дополнительной диагностикой.

Пользователь дополнительно указал чекеры Webshift и Malw. Webshift исключён из списка ненайденных после разбора JavaScript его страницы. У Malw CF найден общий чекер Malw, но самостоятельное различение профиля Cloudflare и обычного профиля не установлено. У MagicDNS найден чекер доступности ИИ; отдельный признак использования именно резолвера MagicDNS пока не найден. «Не найден» описывает результат исследования, а не утверждение об отсутствии сервиса.

Проверка доступных endpoint в текущей сети дала: WLrus — HTTP 200 / `via: public`; Zapret — HTTP 200 / `seen: false` после свежего системного lookup; Malw — сетевую ошибку без результата. Это проверка контракта и отрицательных состояний в текущем подключении, не тест с включением каждого провайдера и не оценка сети другого ПК.

Для реализации: хранить тип официального чекера рядом с записью провайдера, вызывать его через системный путь после применения DNS, не через прямой запрос к выбранному DNS — иначе проверка докажет только доступность самого провайдера. Использовать свежий идентификатор там, где он предусмотрен; проверять явный результат и профиль; ограничить время и число запросов. Тайм-аут, ошибка формата или недоступность сайта означают «Не удалось проверить», а не «DNS не настроен». Для провайдера без проверенного механизма показывать отсутствие подтверждения и предлагать универсальную диагностику.

## Что проверяется сейчас

- `NativeDnsSystem.Set` повторно читает состояние адаптера и сравнивает DNS с запрошенным значением. `EncryptedDns` хранит и применяет параметры шифрования. Это подтверждает настройку Windows, но не принадлежность внешнего рекурсивного узла.
- `SystemDnsVerification.Verify` выполняет системный запрос с обходом локального кэша к `example.com` и `www.microsoft.com`. Ответ подтверждает работоспособность системного разрешения имени, но не выбранного оператора.
- `ResolverCheck` получает от MangoProxy/bash.ws две отдельные выборки для уникальных имён: системный путь и прямой запрос к выбранному провайдеру. В обычном режиме оба пути используют незашифрованный DNS и могут попасть под одинаковое перенаправление.
- `ResolverCheck.Compare` возвращает `Shared`, если совпал хотя бы один адрес. Смешанный набор «ожидаемый узел плюс посторонний» при этом тоже получает `Shared`. Такой результат нельзя использовать как полное подтверждение маршрута.
- Проверки общего DNS не подтверждают отдельные точные правила Antigravity или собственный Secure DNS браузера.

## Предлагаемая проверка после включения

### 1. Настройки на ПК

Зафиксировать сеанс: провайдер и профиль, способ подключения, протокол, ID изменённых адаптеров, IPv4/IPv6, отпечаток сети и время проверки.

Повторно прочитать фактические адреса и режим получения DNS на затронутых адаптерах. Для шифрованного режима отдельно сверить шаблон/имя TLS, разрешённость обычного fallback и необходимые параметры Windows. Учитывать действующие точные NRPT-исключения, а не объявлять весь DNS компьютера однородным.

Статус: «Настройки применены» или «Windows не подтвердила настройки». Наличие одинаковых IP на постороннем виртуальном интерфейсе не равно успешной настройке активного подключения.

### 2. Системный путь и локальный процесс

Выполнить системный запрос к свежему служебному имени, без указания внешнего сервера в самом запросе. Не подменять этот тест прямым запросом к выбранному DNS.

Для способов «Через приложение» и «Gemini / NotebookLM» дополнительно связать уникальный тест с получением запроса рабочим процессом и ответом от выбранного upstream. Нужна корреляция конкретного запроса через IPC; общий счётчик ответов и прямой self-test этого не подтверждают. Уникальный идентификатор хранить только в памяти, не печатать в журнале. Рабочий процесс сообщает профиль провайдера и успешное защищённое соединение, а не только значение выбора в UI.

Для нативного шифрования Windows корректно писать «DoH/DoT настроен». Внешний leak-test не измеряет протокол между ПК и рекурсивным сервером. Не объявлять шифрование подтверждённым на проводе только по IP из внешнего сервиса.

### 3. Наблюдение извне и доверенный контроль

1. Получить отдельные сеансы у наблюдателя для системного пути и контроля. Имена не должны пересекаться.
2. Системные запросы выполнить обычным путём Windows.
3. Контроль выполнить через подтверждённый DoH/DoT **того же профиля** выбранного провайдера с проверкой сертификата. Даже при выборе обычного DNS контроль не должен идти открытым UDP/53. Если подходящего шифрованного endpoint нет или он недоступен — результат «Провайдер не подтверждён», без незаметного ослабления до UDP.
4. Небольшими ограниченными сериями собрать адреса рекурсивных узлов, которые увидел авторитетный сервер. Контрольный пул может меняться: ограниченный повтор помогает уточнить его, но не доказывает полноту списка.
5. Сравнить все системные узлы с контрольным набором. Совпадение одного узла не должно скрывать остальные адреса. Разные пулы или отсутствие пересечения означают отсутствие подтверждения, а не автоматически доказанный перехват.
6. При необходимости использовать независимого второго наблюдателя. MangoProxy и прямой bash.ws не считать двумя независимыми измерениями.

Наблюдатель видит последний рекурсивный узел, который обратился к его зоне. Он может отличаться от входного IP DNS из-за пересылки и архитектуры провайдера. Поэтому не требовать буквального равенства введённому IP; не идентифицировать провайдера только по стране, PTR, ASN или соседнему адресу.

## Результат на главном экране

Состояние включения и состояние проверки маршрута должны быть отдельными. Например:

```
DNS включён
На ПК: применён
Извне: маршрут совпал с защищённым контролем
```

В подробностях: выбранный провайдер/профиль, время, способ и протокол, настроенные адреса, наблюдаемые узлы системного пути, контрольные узлы, источник наблюдения и уровень подтверждения.

Состояния внешней проверки:

- **Маршрут совпал с защищённым контролем** — в полученной выборке нет необъяснённых узлов. Формулировка относится только к этому измерению и тестовым именам.
- **Есть неподтверждённые узлы** — часть адресов совпала, часть не найдена в контрольной выборке; показать обе группы.
- **Выбранный провайдер не подтверждён** — пересечения нет, нет надёжного контроля или данные недостаточны.
- **Не удалось проверить** — недоступен наблюдатель, истёк срок ожидания или изменилась сеть.

Отсутствие наблюдения не является успешной проверкой и не означает поломку уже работающего DNS. Не откатывать и не переприменять сетевые настройки из-за отказа стороннего сайта. При смене сети аннулировать старый результат; не возвращать отменённую пользователем автоматическую перенастройку Wi-Fi.

## Браузер и Antigravity

Проверка из приложения относится к системному пути приложения. Для браузера с собственным DoH нужна отдельная проверка из этого браузера: открытие проверки во встроенном WebView не заменяет запрос из профиля Chrome/Яндекса.

В режиме отдельного Antigravity обычный тестовый домен проверяет основной DNS. Маршрут двух точных API-доменов нужно отражать отдельно по действующей NRPT-политике или коррелированному запросу локального рабочего процесса. Внешнее совпадение общего DNS не подтверждает доступность Antigravity, вход в аккаунт или ответ модели.

## Проверки для реализации

| Сценарий | Ожидаемое поведение |
| --- | --- |
| IP в Windows изменились, но UDP перенаправлен провайдером | Не подтверждать оператора по совпадению двух открытых запросов; использовать защищённый контроль. |
| Системная выборка содержит ожидаемый и посторонний узлы | Показать смешанный результат, не полный успех. |
| IP похожи, совпадает /24 или ASN | Этого недостаточно для подтверждения. |
| У провайдера разные выходные IP или неполный контрольный пул | Осторожный результат с адресами и ограниченным повтором, без автоматического обвинения в утечке. |
| Сертификат контрольного DoH/DoT не проверен | Контроль недоверенный; сертификат не игнорировать, на UDP не переходить. |
| Уникальный системный запрос прошёл через рабочий процесс | Связать его с upstream-ответом; прямой self-test не засчитывать вместо него. |
| Работает IPv4, но присутствует другой активный путь IPv6 | Не объявлять весь ПК подтверждённым без проверки применённых политик обоих семейств. |
| Во время теста изменились сеть, провайдер или режим | Отбросить результат старого сеанса. |
| Наблюдатель недоступен, отмена, пустой/неверный ответ | «Не удалось проверить»; не менять DNS; сбросить предыдущий успех. |
| Браузер использует другой DoH | Системный результат не распространять на браузер. |
| Отдельный DNS Antigravity отличается от основного | Показывать отдельный маршрут и не считать его проверенным общим тестом. |
| Пользователь выключил автопроверку | Не обращаться к внешнему наблюдателю автоматически. |

## Порядок внедрения

1. Добавить официальные проверки Zapret DNS и WLrus как основные проверки этих провайдеров. Сначала закрепить контракт положительного, отрицательного и недоступного результата тестами; отдельно проверить остальные профили.
2. Исправить уровень доверия универсального сравнения: защищённый контроль, смешанные результаты и честные статусы. Сохранить явные отдельные поля настройки и внешнего наблюдения.
3. Добавить корреляцию системного запроса с локальным рабочим процессом и подробный журнал подтверждения.
4. После проверки протокола добавить независимого наблюдателя; затем отдельный пользовательский тест браузера.

Ни один этап не требует сброса Winsock, выключения адаптеров, изменения роутера или автоматического переключения DNS.
